# Phase 34: Case Data Store - Context

**Gathered:** 2026-03-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Fetch case metadata from the SFDC API and OCM CLI inside the container on attach, writing structured JSON files and a sourcing-safe env file to the case workspace directory. Display, search, and restore commands are separate phases.

</domain>

<decisions>
## Implementation Decisions

### File structure

Four files written to the case directory (e.g., `/case/`):

| File | Contents |
|------|----------|
| `sfdc-case.json` | Full raw response from `/v1/cases/{caseNumber}` |
| `sfdc-comments.json` | Full raw SFDC case comments |
| `ocm-cluster.json` | Full output of `ocm get cluster <external_id>` (when available) |
| `case.env` | Normalized key fields extracted from above, for bash sourcing |

No `case.json` — `case.env` covers scripting needs; raw files cover structured access.

### case.env format

- Variable prefix: `MC_` (e.g., `MC_CASE_NUMBER`, `MC_CUSTOMER_NAME`)
- Always quote all values, even simple strings/numbers: `MC_SEVERITY="3"`
- Header comment at top of file showing generation date and case number:
  ```
  # Generated by mc on 2026-03-20 for case 12345678
  ```
- Fields extracted into case.env:
  - `MC_CASE_NUMBER`
  - `MC_CUSTOMER_NAME`
  - `MC_SUMMARY`
  - `MC_SEVERITY`
  - `MC_STATUS`
  - `MC_PRODUCT`
  - `MC_CLUSTER_EXTERNAL_ID` (from SFDC `openshiftClusterID` → OCM `external_id`)
  - `MC_CLUSTER_NAME` (if available from SFDC API)

### OCM cluster field naming

Use OCM field names where possible:
- `external_id` — the external cluster ID, sourced from SFDC `openshiftClusterID`
- `name` — cluster name (if returned by SFDC API)
- Internal OCM `id` — not included (not available from SFDC API, out of scope for this phase)

### Missing field handling

- In JSON files: `null` for absent/unknown values (semantically accurate)
- In `case.env`: empty string `""` for absent/unknown values (safe for bash)
- `MC_CLUSTER_EXTERNAL_ID=""` is always present even when unknown (never absent)

### OCM cluster data fetch

- When `external_id` is available: run `ocm get cluster <external_id>` and write output to `ocm-cluster.json`
- If `ocm get cluster` fails for any reason (not logged in, cluster not found, network): print a warning to the terminal, then continue — no `ocm-cluster.json` written

### Write timing

- Data is fetched and files are written **inside the container** (not on the host), triggered by `mc` running in agent mode as part of the attach sequence — before the interactive shell opens
- Files are **always refreshed** on every attach (overwritten, not skipped if already present)

### Failure behavior

- If the SFDC API call fails (bad token, network issue): print a warning to the terminal, then open the interactive shell anyway
- Partial data (e.g., SFDC succeeded but OCM failed) is acceptable — write what succeeded

### Claude's Discretion

- Exact warning message wording
- Order of operations (SFDC fetch → OCM fetch → write env → open shell)
- How `mc` agent mode invokes this sequence (entrypoint vs attach hook)
- Whether `sfdc-comments.json` fetch is concurrent with `sfdc-case.json` or sequential

</decisions>

<specifics>
## Specific Ideas

- OCM naming convention should be followed: field names in `case.env` should mirror OCM terminology (e.g., `external_id` not `cluster_id`)
- The SFDC API field `openshiftClusterID` maps to OCM's `external_id` — this translation is explicit
- Files live in the case directory accessible inside the container (e.g., `/case/`)

</specifics>
